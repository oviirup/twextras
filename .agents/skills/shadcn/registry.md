# Registry Authoring and Addresses

Reference for creating, fixing, publishing, or reasoning about a shadcn registry.

## Mental Model

Registry has two forms:

- **Source registry**: authored `registry.json` in project/repo. May use `include` + file paths pointing at source files.
- **Built registry**: generated JSON files served to CLI consumers, usually from `public/r`. `npx shadcn@latest build` creates this.

CLI installer consumes registry item payloads. Source registry = way to author payloads from real files.

Registry items not limited to React components: components, hooks, utilities, design tokens, pages, config files, docs, rules, workflows, templates, MCP files, other project files.

## Root `registry.json`

Root file defines registry metadata + either `items` or `include`.

```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "acme",
  "homepage": "https://acme.com",
  "items": [
    {
      "name": "absolute-url",
      "type": "registry:lib",
      "title": "Absolute URL",
      "description": "A utility to turn any path into an absolute URL.",
      "files": [
        {
          "path": "lib/absolute-url.ts",
          "type": "registry:lib"
        }
      ]
    }
  ]
}
```

Root rules:

- Must include `name` + `homepage`.
- `items` = array of item definitions.
- `include` may split source registry into multiple files.
- Included files may omit `name` + `homepage`.

## Include

`include` keeps large registries modular.

```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "acme",
  "homepage": "https://acme.com",
  "include": ["registry/ui/registry.json", "registry/blocks/registry.json"]
}
```

Include rules:

- Paths relative to declaring `registry.json`.
- Must explicitly point to a `registry.json` file.
- No remote URLs, absolute paths, or `..` traversal.
- Item file paths relative to registry file declaring item.
- Duplicate item names fail across resolved registry.

Included file example:

```json
{
  "items": [
    {
      "name": "button",
      "type": "registry:ui",
      "files": [
        {
          "path": "button.tsx",
          "type": "registry:ui"
        }
      ]
    }
  ]
}
```

File at `registry/ui/registry.json` → `button.tsx` read from `registry/ui/button.tsx`, built item path emitted relative to root registry.

## Item Definitions

Common fields:

```json
{
  "name": "login-form",
  "type": "registry:block",
  "title": "Login Form",
  "description": "A login form with email and password fields.",
  "dependencies": ["zod"],
  "registryDependencies": ["button", "input", "label"],
  "files": [
    {
      "path": "blocks/login-form.tsx",
      "type": "registry:block"
    }
  ],
  "cssVars": {
    "light": {
      "brand": "oklch(0.62 0.18 250)"
    },
    "dark": {
      "brand": "oklch(0.72 0.16 250)"
    }
  }
}
```

Important fields:

- `name`: installable item name, not necessarily file path.
- `type`: registry item type — `registry:ui`, `registry:block`, `registry:lib`, `registry:hook`, `registry:file`, `registry:page`, `registry:theme`, `registry:style`, `registry:font`, `registry:item`.
- `files`: source files copied/generated by item.
- `dependencies`: npm runtime deps.
- `devDependencies`: npm dev deps.
- `registryDependencies`: other registry items required.
- `cssVars`, `css`, `tailwind`, `envVars`, `docs`: optional install-time additions.

File rules:

- Paths relative to declaring `registry.json`.
- `registry:file` + `registry:page` files require `target`.
- No remote file URLs in source registry file paths.
- Source files copy-pasteable: no hidden app-only imports.

## Registry Dependencies

`registryDependencies` = item addresses, not file paths.

```json
{
  "name": "login-form",
  "type": "registry:block",
  "registryDependencies": ["button", "@acme/input", "acme/ui/card#v1.2.0"],
  "files": [
    {
      "path": "blocks/login-form.tsx",
      "type": "registry:block"
    }
  ]
}
```

Dependency rules:

- Bare names (`"button"`) = official shadcn items. Never same-registry/repo items.
- Namespaced → `@namespace/item-name`.
- GitHub → `owner/repo/item-name`.
- Pin GitHub deps `owner/repo/item-name#ref` when needed.
- Refs not inherited: `owner/repo/foo#v2` depending on `bar` same repo at `v2` → write `owner/repo/bar#v2`.
- No relative deps like `"./bar"`.

## Address Schemes

Classify registry item string first.

| Address                             | Scheme    | Meaning                                                      |
| ----------------------------------- | --------- | ------------------------------------------------------------ |
| `button`                            | shadcn    | Official shadcn item `button`.                               |
| `@acme/button`                      | namespace | Item `button` from configured `@acme`.                       |
| `@acme/ui/button`                   | namespace | Item `ui/button` from configured `@acme`.                    |
| `https://example.com/r/button.json` | url       | Built registry item JSON at URL.                             |
| `./button.json`                     | file      | Built registry item JSON on disk.                            |
| `acme/ui/button`                    | github    | Item `button` from GitHub repo `acme/ui`.                    |
| `acme/ui/forms/login#main`          | github    | Item `forms/login` from GitHub repo `acme/ui` at ref `main`. |

Namespace + GitHub addresses: slashful item names allowed, item names not file paths. Addresses ending `.json` keep file-address precedence — `acme/ui/data/schema.json` treated as file path, not GitHub item.

## GitHub Registries

Public GitHub repo = source registry when it has root `registry.json`.

```txt
owner/repo/item-name[#ref]
```

Rules:

- First two path segments = GitHub owner + repo.
- Remaining segments = registry item name.
- Source entrypoint = always root `registry.json`.
- GitHub registries = source registries consumed directly by CLI. No `shadcn build` or generated item JSON needed.
- `include` follows same source-registry rules as local.
- Currently public `github.com` repos only. Private repos + GitHub Enterprise require explicit product decisions.

Implementing GitHub fetching → resolve refs to commit SHA before reading source files. Don't read moving refs directly from `raw.githubusercontent.com` — branch-like refs cache several minutes.

Preferred flow:

```txt
owner/repo[#ref]
  -> resolve ref with git ls-remote
  -> commit SHA
  -> read https://raw.githubusercontent.com/{owner}/{repo}/{sha}/registry.json
  -> read includes + item files from same SHA
```

Keeps command on one consistent snapshot. Full 40-char SHAs stable, usable directly. Branches, tags, short refs need Git to resolve to SHA first.

## Build and Verify

Build source registries:

```bash
npx shadcn@latest build
npx shadcn@latest build registry.json --output public/r
```

Inspect result:

```bash
npx shadcn@latest list @acme
npx shadcn@latest search @acme -q "login"
npx shadcn@latest view @acme/login-form
npx shadcn@latest add @acme/login-form --dry-run
npx shadcn@latest registry validate ./registry.json
```

Public GitHub registries directly:

```bash
npx shadcn@latest list owner/repo
npx shadcn@latest search owner/repo -q "login"
npx shadcn@latest view owner/repo/item
npx shadcn@latest add owner/repo/item --dry-run
npx shadcn@latest registry validate owner/repo
```

Working on registry implementation in shadcn/ui codebase:

- Keep address parsing pure + testable.
- No side effects in validators.
- Preserve existing behavior for official shadcn, namespace, URL, file schemes.
- Tests for address parsing, source loading, dependency resolution, list, search, view, add paths.
- Prefer small source-reader abstractions over plugin system until multiple real providers.
